# Журнал решений

Каждая запись: решение, причина, отвергнутые альтернативы. Новые решения добавляются в конец.

### 1. Игровая логика на Morpeh ECS
MonoBehaviour остаются только для приложения и view. Причины: явный порядок систем, данные отдельно от поведения, простое расширение. Старый подход (MonoBehaviour-компоненты `AttackComponent`, `DashComponent`) удалён.

### 2. Конфиги на трейтах: `EntityConfig<TTrait>`
Конфиг — список `[SerializeReference]` трейтов, каждый ставит свои компоненты. Отдельные маркеры `IAgentTrait` и `IWeaponTrait`, чтобы в инспекторе оружия не показывались трейты агента. Отвергнуто: монолитные конфиги и разнесение по отдельным ScriptableObject — инициализатор всё равно знал бы устройство каждой фичи. Риск: `SerializeReference` теряет данные при переименовании класса — использовать `[MovedFrom]`.

### 3. Универсальный агент вместо класса Player
Игрок и враги — агенты с разными трейтами. Источник управления — тоже трейт: `PlayerControlTrait`, `AiBrainTrait`.

### 4. Конвейер скорости разбит на группы
Reset (300) → источники (Dash, Movement) → Apply (600). Отвергнуто: класть Dash внутрь `MovementFeature` — Movement начал бы знать обо всех источниках скорости.

### 5. Состояние — это наличие компонента
`Dashing`, `AttackSwing`, `Dead`. Фильтры выражают условия без ветвлений, состояние видно в инспекторе Morpeh.

### 6. Запросы чистит система того же типа обновления, что и потребитель
`DashRequest` ставится из колбэка ввода (до Update), а потребляется в FixedUpdate. Очистка в Update или cleanup теряла бы запросы в кадрах без fixed-тика.

### 7. Оружие — отдельная сущность
Свои компоненты для каждого типа оружия, смена — заменой ссылки, враги используют ту же систему. Отвергнуто: компоненты оружия на агенте.

### 8. Системы фаз идут в обратном порядке переходов
Recovery → Swing → Charge → Start. Фаза, появившаяся в кадре, начинает отсчёт со следующего — без потери времени.

### 9. Ввод пишет состояние и запрос: `AttackIntent.Held` + `AttackRequest`
Удержание нужно для заряда, запрос — для старта по нажатию (без автоповтора при удержании). ИИ пишет те же компоненты.

### 10. `AimRay` отвязывает ближний бой от камеры
Игроку луч заполняет `CameraAimSystem`, врагам — ИИ. Отвергнуто: `Camera` в системе попаданий.

### 11. События урона — отдельные сущности
В Morpeh нет буферов на сущности. Компонент на цели перезаписался бы вторым ударом за кадр. Сущность-событие проходит конвейер модификаторов и удаляется в cleanup.

### 12. Блокировки — флаги причин
`MovementBlockers`, `ActionBlockers`, `DamageImmunity`. Новая причина (стан, катсцена) — новый флаг, системы не меняются. Отвергнуто: `Without<Dead>` в каждой системе старта.

### 13. Мир принадлежит `GameplayEntry`
`World.Create()` при инициализации сцены, `Dispose()` в `OnDestroy`. С `World.Default` перезапуск сцены падал на дубликате ключа группы, а старые сущности и подписки на ввод оставались жить.

### 14. UI оружия на Canvas, данные через MessagePipe
Спрайт оружия от первого лица — это HUD. Тайминг считается только в ECS, оверлей лишь отображает. Канал — MessagePipe, потому что оверлеи создаются в корневом скоупе и не видят gameplay-скоуп. Создание оверлеев идемпотентно. Привязка их жизни к сцене пока не сделана.

### 15. Utility AI, действия ИИ — отдельные сущности
Добавить действие = трейт + исполнитель, выбор не меняется. Соображения — данные в инспекторе (кривые). Бонус инерции убирает дрожание между действиями. «Поиск» получается сам из затухания оценки Chase. Отвергнуты: FSM (переходы разрастаются) и Behaviour Tree (вторая модель исполнения рядом с ECS).

### 16. NavMesh-запросы + своё следование, без `NavMeshAgent`
`NavMeshAgent` двигал бы тело в обход конвейера Velocity → Rigidbody и конфликтовал бы с дашем и физикой.

### 17. Восприятие опрашивается с интервалом и разносом
Raycast-проверки 5 раз в секунду со случайной стартовой фазой у каждого врага. Память о цели — отдельный таймер каждый кадр.

### 18. `Position` синхронизируется из view каждый кадр
Раньше `Position` записывалась только при спавне, и восприятие видело бы устаревшие координаты. Источник истины для позиции — Transform view (Rigidbody).

### 19. Агенты, расставленные на сцене: `AgentAuthoring` + `FindObjectsByType` при инициализации
Дизайнер расставляет врагов прямо в сцене, отдельный префаб и Addressables не нужны. Поиск по сцене делается один раз при старте, как при бейкинге.

### 20. Реакция на смерть — трейт
`DestroyOnDeathTrait` сейчас, `SpawnOnDeathTrait` для лута позже. Игрок без этого трейта: его смерть ведёт к перезапуску сцены.

### 21. Камера на оси капсулы
Смещение камеры вперёд (0.47 при радиусе капсулы 0.5) выводило near plane за капсулу — камера проваливалась в стены. Поворот тела вслед за камерой проблему не решает.

### 22. Billboard через bind + `ILateSystem`
Спрайт поворачивается к камере после её обновления. Логический `FacingDirection` отделён от визуала: на нём построятся 8-направленные спрайты.

### 23. Запуск сцены из редактора без сейва
`ReloadGameplay` при отсутствии сейва грузит уровень 0 и не сохраняет. Это компромисс для удобства разработки.

### 24. Капсулы агентов без трения
`AgentFrictionless` (трение 0, combine `Minimum`). Горизонтальную скорость задаёт конвейер, поэтому трение не нужно для остановки, а прилипание к стенам оно вызывало. Отвергнуто: обнулять составляющую скорости в стену вручную — тот же результат, но больше кода и запросов к физике. Цена: сползание по склонам, когда они появятся.
